# 计划拆分与进度追踪 Skill

## 基本信息

| 属性 | 值 |
|------|-----|
| Skill名称 | plan-breakdown-tracking |
| 所属Agent | PM Agent |
| 用途 | 将全局执行计划中的每个任务拆分为独立子计划文件，每个文件包含从结果蓝图提取的完整上下文和最终结果，确保子计划可独立执行且严格遵循蓝图 |

## 核心理念

**独立子计划，蓝图可追溯**：每个子计划是独立的文件，包含该计划所需的完整上下文和最终结果。子计划的内容严格从结果蓝图中拆解，Agent在执行子计划时无需重新思考"最终目标"，所有信息已在子计划文件中明确。

**每个子计划即蓝图的一块拼图**：所有子计划合起来构成完整的结果蓝图。每个子计划完成时，对应的蓝图部分即达成。

## 触发条件

全局执行计划概览完成后，PM Agent调用本Skill进行子计划拆分。

## 前置依赖

- `global-execution-planning` Skill已执行完成
- 全局执行计划概览已产出
- 结果蓝图已锁定（人类已确认）

## 执行步骤

### 步骤1：从结果蓝图提取每个任务对应的终态内容

对于全局执行计划概览中的每个任务（T-XX），从结果蓝图中提取该任务对应的终态内容：

1. 读取结果蓝图 `agent-doc/result-first/result-definition.md`
2. 根据任务的"对应蓝图项"，定位结果蓝图中的具体章节
3. 提取该章节的全部内容（包含线框图、交互元素表、API定义、字段定义等）

### 步骤2：创建独立子计划文件

**每个子计划必须是一个独立的文件**，不得合并到同一个文件中。

文件命名规范：
```
plan/[确认日期]/SP-XX-[任务简短描述].md
```
示例：`plan/2026-05-29/SP-01-project-init.md`

#### 子计划文件模板

每个子计划文件必须包含以下结构，确保Agent执行时无需参考其他文档也能明确最终目标：

```markdown
# SP-XX: [子计划名称]

## 元信息

| 属性 | 值 |
|------|-----|
| 子计划编号 | SP-XX |
| 对应全局任务 | T-XX |
| 对应结果蓝图章节 | [蓝图中的章节或项] |
| 前置依赖子计划 | SP-XX, SP-XX |
| 输出产物 | [具体产物及存放路径] |
| 执行Agent | [Agent名称] |
| 预估复杂度 | [低/中/高] |

## 最终结果（来自结果蓝图）

> 本节内容直接从结果蓝图中提取，是执行本子计划的终极目标。
> Agent必须以此为准，不得自行修改或重新定义。

### 要实现的内容

[从结果蓝图中提取该子计划需要实现的完整内容，包含：
- 如果是前端页面：页面线框图、交互元素表（全部字段/按钮）、表单校验规则、导航关系
- 如果是后端API：API路径/方法/请求参数/响应格式/状态码、处理链路
- 如果是数据表：表名、字段列表（每个字段的/类型/约束/索引）、初始数据
- 如果是业务逻辑：业务规则、状态流转、管理维度
]

### 验收标准

对应结果蓝图中的以下项必须全部达成：

| 蓝图项 | 验收条件 | 状态 |
|--------|---------|------|
| [蓝图项编号或描述] | [判断条件] | ⬜ |

## 上下文信息

### 输入依赖

| 输入项 | 来源 | 说明 |
|--------|------|------|
| [需要的输入] | [来源子计划/外部] | [用途说明] |

### 相关设计文档引用

| 文档 | 相关章节 |
|------|---------|
| [设计文档名称] | [章节] |

## 执行步骤

| 步骤 | 操作描述 | 预期中间产物 | 参考蓝图项 |
|------|---------|-------------|-----------|
| 1 | [具体操作] | [中间产出] | [对应的蓝图项] |
| 2 | [具体操作] | [中间产出] | [对应的蓝图项] |
| 3 | [具体操作] | [中间产出] | [对应的蓝图项] |

## 完成标志

- [ ] 所有验收标准已达成
- [ ] 输出产物已产出并存放至指定路径
- [ ] 实际产出与结果蓝图中的描述一致

---

> 本子计划依据结果蓝图 `agent-doc/result-first/result-definition.md` 制定。
> 如有任何偏差，以结果蓝图为最终判断标准。
```

### 步骤3：建立子计划关联关系

1. **输入关联**：在当前子计划的"前置依赖"中标注需要哪些子计划先完成
2. **输出关联**：在进度表中确认当前子计划的产物被哪些子计划使用
3. **校验**：A依赖B，则B的"输出产物"必须包含A需要的输入

### 步骤4：创建进度追踪总表

创建一个进度追踪总表文件 `plan/[确认日期]/progress.md`，仅包含轻量摘要：

```
# [项目名称] - 进度追踪表

| 子计划 | 任务名称 | 前置依赖 | 对应蓝图项 | 状态 | 完成标志 |
|--------|---------|---------|-----------|------|---------|
| SP-01 | [名称] | 无 | [蓝图章节] | ⬜待开始 | [产物] |
| SP-02 | [名称] | SP-01 | [蓝图章节] | ⬜待开始 | [产物] |

状态说明：
- ⬜待开始 → 🔄进行中 → ✅已完成
- ⚠️有偏差（实际与蓝图不一致）
- ❌阻塞（前置依赖未完成）
```

### 步骤5：校验子计划覆盖完整性

1. **蓝图全覆盖校验**：检查所有子计划的"对应结果蓝图章节"是否覆盖了结果蓝图的所有章节
2. **无遗漏校验**：结果蓝图覆盖矩阵中的每一项都有对应的SP-XX
3. **依赖闭环校验**：检查是否存在循环依赖
4. **独立性校验**：每个子计划文件是否独立包含完整的上下文和目标描述，Agent能否不依赖外部文档即可执行

### 步骤6：输出目录结构

```
plan/[确认日期]/
├── progress.md              ← 进度追踪总表（轻量摘要）
├── SP-01-project-init.md    ← 子计划1：项目初始化
├── SP-02-database-create.md ← 子计划2：数据库创建
├── SP-03-backend-setup.md   ← 子计划3：后端框架搭建
├── SP-04-api-user.md        ← 子计划4：用户API实现
├── SP-05-frontend-login.md  ← 子计划5：登录页面
└── ...                      ← 每个任务一个独立文件
```

## 输入

| 序号 | 输入项 | 来源 |
|------|--------|------|
| 1 | 结果蓝图 | `agent-doc/result-first/result-definition.md` |
| 2 | 全局执行计划概览 | `plan/[yyyy-MM-dd]-global-execution-plan.md` |
| 3 | 各设计文档 | `agent-doc/architecture/`, `agent-doc/technical-design/` |

## 输出

| 序号 | 输出项 | 存放位置 |
|------|--------|----------|
| 1 | N个独立子计划文件 | `plan/[确认日期]/SP-XX-xxx.md` |
| 2 | 进度追踪总表 | `plan/[确认日期]/progress.md` |

## 进度更新规则

每个子计划完成后，PM Agent必须：

1. 更新进度追踪总表中该子计划状态为✅已完成
2. 记录实际产出，与子计划中的"验收标准"逐项比对
3. 如有偏差，标注⚠️并记录偏差内容
4. 通知依赖该子计划的下游子计划可以开始

## 注意事项

1. **每个子计划必须是独立文件**，不得将多个子计划写入同一个文件
2. 子计划中的"最终结果"部分必须直接从结果蓝图中复制，不得重新概括或简化
3. Agent执行子计划时，不得要求Agent"参考结果蓝图"——蓝图相关内容已提取到子计划文件中
4. 子计划中的"验收标准"必须与结果蓝图中的描述严格一致
5. 前置依赖只标注文件路径和输入内容，不复制其他子计划的执行步骤
6. 所有子计划文件合起来必须完整覆盖结果蓝图，不能有遗漏
7. 进度追踪总表只做状态追踪，不包含详细内容——详细内容在各自的子计划文件中
