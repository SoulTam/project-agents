# 结果先行定义 Skill

## 基本信息

| 属性 | 值 |
|------|-----|
| Skill名称 | result-first-definition |
| 所属Agent | PM Agent |
| 用途 | 在项目初期定义应用完成时的完整终态样貌 |

## 核心理念

**结果先行**：在架构和代码还未产出之前，先定义应用"成熟时的样子"。这不是设计文档，而是对最终产品的完整描述——让所有人（包括人类用户）在动手之前就能看到目标。

## 触发条件

PM Agent收到增强后的结构化提示词后，在分发任务之前，必须先调用本Skill进行结果先行定义。

## 执行步骤

### 步骤1：识别需求范围

根据增强后的提示词，识别项目类型和涉及的功能域：

1. 识别技术栈要求（前端框架、后端框架、数据库、部署环境等）
2. 识别核心业务对象（用户需要管理什么、操作什么）
3. 识别用户角色（谁使用这个系统，不同角色做什么）
4. 识别关键约束（性能要求、安全要求、集成要求等）

### 步骤2：调用相关Agent产出终态描述

按以下维度，调用对应Agent分别产出终态描述：

#### 2.1 前端终态定义（调用功能设计Agent产出）

为每个页面/视图输出以下信息：

```markdown
### [页面名称]

**页面用途**：该页面的核心目的

**页面线框图**：

使用ASCII字符绘制线框图，必须标注每个区域的用途和内容。线框图是必须项，不得省略。

```
┌─────────────────────────────────────────────────────────┐
│ [顶部导航栏: Logo / 菜单项 / 用户头像]                    │
├──────────┬──────────────────────────────────────────────┤
│          │                                              │
│ [左侧    │  [主内容区: 核心内容/数据展示]                  │
│  侧边栏] │                                              │
│          │  ┌──────────────────────────────────────┐    │
│ - 菜单1  │  │ [卡片/表格/表单等具体组件]             │    │
│ - 菜单2  │  │                                      │    │
│ - 菜单3  │  └──────────────────────────────────────┘    │
│          │                                              │
├──────────┴──────────────────────────────────────────────┤
│ [底部: 状态栏/版权信息]                                   │
└─────────────────────────────────────────────────────────┘
```

**页面布局说明**：
- 顶部：[描述导航栏内容和操作]
- 左侧：[描述侧边栏菜单和功能]
- 主内容区：[描述核心内容展示方式和数据来源]
- 右侧/底部：[描述辅助信息和操作]

**交互元素**：

| 元素 | 类型 | 功能描述 | 触发行为 |
|------|------|---------|---------|
| [按钮名称] | 按钮 | [做什么] | [点击后发生什么] |
| [表单名称] | 表单 | [提交什么] | [提交后处理] |
| [列表/表格] | 数据展示 | [展示什么] | [操作行为] |

**表单详情**（如有表单）：

| 字段名 | 类型 | 必填 | 校验规则 | 默认值 |
|--------|------|------|---------|--------|

**页面间导航**：
- 从[页面A]到本页面：通过[什么操作]
- 从本页面到[页面B]：通过[什么操作]
```

#### 2.2 后端终态定义（调用技术设计Agent产出）

为后端服务输出以下信息：

```markdown
### 服务概览

| 服务名称 | 职责 | 对应前端操作 |
|----------|------|-------------|

### API完整列表

| API路径 | 方法 | 功能 | 请求参数 | 响应格式 | 对应前端操作 |
|---------|------|------|---------|---------|-------------|

### 后端处理链路

为每个核心业务流程描述完整链路：

**[业务流程名称]**：
```
请求 → [步骤1:做什么] → [步骤2:做什么] → ... → 响应
```
- 每个处理环节的职责
- 环节之间的数据传递
- 异常处理方式
```

#### 2.3 数据层终态定义（调用技术设计Agent产出）

```markdown
### 数据库表/集合设计

| 表名 | 用途 | 核心字段 | 索引 |
|------|------|---------|------|

### 数据流向图

用Mermaid描述数据如何在各功能模块间流动：

```mermaid
graph LR
    A[数据源] --> B[处理模块]
    B --> C[存储]
    C --> D[查询服务]
```

### 数据使用方式

| 功能模块 | 使用的数据 | 操作类型(CRUD) | 频率 |
|----------|-----------|---------------|------|
```

#### 2.4 业务逻辑终态定义（调用需求分析Agent产出）

```markdown
### 核心业务对象生命周期

为每个核心业务对象描述完整生命周期：

**[业务对象名称]**：
- 创建条件：[什么时候创建]
- 状态流转：状态A → 状态B → 状态C（用Mermaid状态图表达）
- 销毁条件：[什么时候删除/归档]

### 业务规则

| 规则编号 | 规则描述 | 适用场景 | 约束 |
|----------|---------|---------|------|

### 管理维度

| 管理对象 | 可执行操作 | 操作者权限 | 操作边界 |
|----------|-----------|-----------|---------|
```

### 步骤3：整合产出应用终态描述文档

将各Agent的终态描述整合为一份完整的"应用终态描述文档"，存放至`agent-doc/result-first/`目录。

文档结构：

```
# [项目名称] - 应用终态描述

## 1. 项目概述
- 项目目标
- 技术栈
- 用户角色

## 2. 前端终态
- 所有页面的布局、交互、导航

## 3. 后端终态
- 服务列表、API列表、处理链路

## 4. 数据层终态
- 表设计、数据流向、数据使用方式

## 5. 业务逻辑终态
- 业务对象生命周期、业务规则、管理维度

## 6. 非功能性终态
- 性能指标
- 安全要求
- 可扩展性设计
```

### 步骤4：暂停等待人类确认

将应用终态描述文档提交给人类用户审阅，**必须等待人类明确确认后才能进入下一阶段**。

如人类提出修改意见，按意见修改后重新提交确认。

## 输入

| 序号 | 输入项 | 来源 |
|------|--------|------|
| 1 | 增强后的结构化提示词 | PM Agent |

## 输出

| 序号 | 输出项 | 存放位置 |
|------|--------|----------|
| 1 | 应用终态描述文档 | `agent-doc/result-first/result-definition.md` |

## 注意事项

1. 终态描述不是设计文档，不需要说明"如何实现"，只需要描述"完成后是什么样子"
2. 每个交互元素都必须有明确的功能描述和触发行为，不能有模糊的按钮或表单
3. **每个前端页面必须配备ASCII线框图**，线框图必须标注每个区域的用途和内容，线框图不得省略，不得用纯文字描述替代
4. 后端处理链路必须完整，从请求到响应的每一步都要描述
5. 数据流向必须闭环，数据从哪来、到哪去、如何被使用都要描述清楚
6. 终态描述是人类用户确认目标的唯一依据，必须足够详细让人类能判断是否符合预期
