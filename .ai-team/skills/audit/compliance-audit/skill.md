# 合规稽查 Skill

## 基本信息

| 属性 | 值 |
|------|-----|
| Skill名称 | compliance-audit |
| 所属Agent | 稽查Agent |
| 用途 | 检查各Agent工作流程和产出物是否符合`.ai-team/`文档规范 |

## 核心理念

**依据唯一**：以`.ai-team/`目录下的所有文档作为唯一判断依据，不引入任何外部知识、主观判断或创造性解释。严格按照文档字面含义执行稽查。

## 触发条件

| 序号 | 触发条件 | 触发者 |
|------|----------|--------|
| 1 | 子计划执行完成后 | PM Agent自动触发 |
| 2 | 人类用户主动请求 | 人类用户 |
| 3 | Agent产出物完成时 | PM Agent |
| 4 | 整改验证时 | 稽查Agent自身 |

## 执行步骤

### 步骤1：加载稽查依据

读取以下文档作为稽查依据：

1. 读取`.ai-team/rules/global-rules.md` - 全局规则
2. 读取`.ai-team/agents/`下所有`agent.md` - Agent定义
3. 读取`.ai-team/skills/`下相关`skill.md` - Skill定义
4. 读取`.ai-team/knowledge-base/`下相关文档 - 知识库
5. 读取`.cursorrules` - 主规则文件

### 步骤2：确定稽查范围

根据触发条件确定本次稽查范围：

| 触发类型 | 稽查范围 |
|----------|----------|
| 子计划完成 | 该子计划的产出物 + 执行过程 + 相关Agent行为 |
| 人类请求 | 指定范围或全部Agent全流程 |
| 产出物完成 | 该产出物的格式、内容、存放路径 |
| 整改验证 | 被整改Agent的整改结果 |

### 步骤3：执行稽查检查

按照稽查检查项逐项检查：

#### 3.1 流程合规检查

```
检查清单：
□ 提示词工程师Agent是否先于PM Agent处理请求
□ 任务性请求是否先输出执行计划
□ 执行计划是否经人类确认
□ 结果先行定义是否在开发前完成
□ 终态描述后是否暂停等待人类确认
□ **结果蓝图是否完整（全量覆盖，不仅是核心信息）**
□ **完整性自检是否执行并通过（15项检查）**
□ **交叉维度完整性校验是否执行并通过**
□ **待确认项是否已清零**
□ 设计文档是否基于终态反推
□ 全局计划是否为轻量概览（仅任务+依赖）
□ **每个子计划是否为独立文件（plan/[日期]/SP-XX-xxx.md）**
□ **子计划是否从蓝图直引最终结果（非概括）**
□ **子计划是否有剩余不确定性（如"参考蓝图"等模糊指示）**
□ **子计划是否全覆盖蓝图（所有蓝图项有对应子计划）**
□ 子计划间前置依赖是否正确标注
□ 每完成子计划是否更新进度总表
□ 所有子计划完成后是否执行终态回溯校验
□ 每步执行后是否校验实际与计划一致性
```

#### 3.2 产出物格式检查

```
检查清单：
□ 结果蓝图是否包含前端终态（含ASCII线框图，每页标注区域用途和内容）
□ 结果蓝图是否包含后端终态（服务列表、API列表、处理链路）
□ 结果蓝图是否包含数据层终态（表设计、数据流向）
□ 结果蓝图是否包含业务逻辑终态（业务对象生命周期、业务规则、管理维度）
□ **结果蓝图是否包含覆盖矩阵（前端-API/API-数据/业务规则-全维度）**
□ **结果蓝图完整性自检是否通过（15项检查项记录）**
□ **交叉维度完整性校验是否通过并有结论记录**
□ **全局计划是否为轻量概览（无详细步骤）**
□ **子计划是否为独立文件（每个 `plan/[日期]/SP-XX-xxx.md` 一个）**
□ **子计划"最终结果"是否从蓝图直引（非重新概括）**
□ **子计划中是否有剩余不确定性（如"参考蓝图"等模糊指示）**
□ **子计划是否全覆盖蓝图（所有蓝图项有对应子计划）**
□ 产出物是否包含思考过程/推理过程/内心独白
□ 是否使用Markdown格式
□ 结构化输出是否使用表格，子项用阿拉伯数字标注
□ 对话结尾是否输出Agent责任记录表
□ 进度追踪总表格式是否正确
```

#### 3.3 规则遵循检查

```
检查清单：
□ 产出物是否包含假设性问题/建议
□ 代码是否使用伪代码/假设性代码/mock（测试除外）
□ Java异常包装是否保存原异常信息
□ Git提交是否遵循Conventional Commits规范
□ 敏感信息是否硬编码
□ 超过两句话的用户请求是否记录到user-request/
□ Session请求数是否超限（5个）
□ 知识点是否经用户确认后写入知识库
```

#### 3.4 路径规范检查

```
检查清单：
□ 文档产出物是否在agent-doc/目录下
□ 代码产出物是否在output/code/目录下
□ 执行计划是否在plan/目录下
□ 同一目录是否只存放同一类型文件
□ 各子目录是否按规范分类（requirements/architecture/feature-design等）
```

### 步骤4：记录不合规项

对每个不合规项记录以下信息：

| 字段 | 说明 |
|------|------|
| 检查项 | 对应稽查检查项编号 |
| 依据条款 | 文档路径 + 条款编号/内容 |
| 实际情况 | 当前实际状态描述 |
| 差距描述 | 实际与要求的差距 |
| 整改要求 | 具体的整改方向和要求 |
| 被稽查Agent | 需要整改的Agent名称 |

### 步骤5：产出稽查报告

按照稽查报告格式产出完整报告，存放至`agent-doc/audit/audit-report-{timestamp}.md`。

### 步骤6：发出整改要求

对存在不合规项的Agent发出整改要求：

1. **引用依据**：必须引用具体文档路径和条款
2. **说明差距**：说明当前实际情况与要求的差距
3. **明确要求**：给出具体的整改要求（不是建议，是要求）
4. **直接发出**：在对话中直接发出给被稽查Agent

整改要求格式：

```
## 整改要求 - {Agent名称}

| 序号 | 整改项 | 依据 | 当前情况 | 整改要求 |
|------|--------|------|----------|----------|
| 1 | {item} | {rule_reference} | {actual} | {rectification} |

请立即执行整改，整改完成后报告结果。
```

### 步骤7：验证整改结果

被稽查Agent整改完成后，稽查Agent执行验证：

1. 重新读取整改后的产出物
2. 逐项比对整改要求是否落实
3. 记录验证结果（通过/未通过）
4. 更新稽查报告中的状态

### 步骤8：更新稽查报告

将验证结果更新到稽查报告中，完成稽查闭环。

## 输入

| 序号 | 输入项 | 来源 |

| 2 | 稽查范围（可选） | PM Agent / 人类用户 |
