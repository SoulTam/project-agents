# 接口类型选择策略

> 本策略指导开发Agent在技术设计和代码实现时，判断模块间交互应采用HTTP API、程序直接调用还是Interface定义。

## 三种接口类型

| 类型 | 定义 | 通信方式 |
|------|------|----------|
| HTTP API | 通过HTTP协议暴露的RESTful接口，跨网络调用 | 网络请求（同步/异步） |
| 程序直接调用 | 同一进程内，一个类直接调用另一个类的方法 | 方法调用 |
| Interface定义 | 通过Java Interface定义契约，实现类可替换，面向接口编程 | 方法调用（多态） |

## 决策规则

| 序号 | 判断条件 | 选择策略 | 原因 |
|------|----------|----------|------|
| 1 | 调用方与被调用方部署在不同服务/进程 | HTTP API | 跨进程必须通过网络通信 |
| 2 | 调用方与被调用方在同一服务同一进程，且调用关系固定不变 | 程序直接调用 | 无需抽象，简单直接 |
| 3 | 调用方与被调用方在同一服务同一进程，但实现可能切换（如支付渠道、存储方式） | Interface定义 | 面向接口编程，支持多实现替换 |
| 4 | 调用方与被调用方在同一服务同一进程，但需要Mock测试或未来可能替换 | Interface定义 | 便于单元测试Mock，预留扩展点 |
| 5 | 同一进程内，模块间有明确领域边界，需解耦 | Interface定义 | 通过接口隔离领域边界，降低耦合 |
| 6 | 前端与后端之间 | HTTP API | 前后端分离架构，跨运行环境 |
| 7 | 同一进程内，工具类/纯函数调用 | 程序直接调用 | 工具方法无状态无多态需求，无需抽象 |
| 8 | 第三方服务/外部系统 | HTTP API | 外部系统通过协议通信 |

## 决策流程

```
调用方和被调用方是否部署在不同服务/进程？
├── 是 → HTTP API
└── 否（同一进程内）
    ├── 是否需要支持多种实现或未来替换？
    │   ├── 是 → Interface定义
    │   └── 否
    │       ├── 是否有明确领域边界需解耦？
    │       │   ├── 是 → Interface定义
    │       │   └── 否
    │       │       ├── 是否需要Mock测试？
    │       │       │   ├── 是 → Interface定义
    │       │       │   └── 否
    │       │       │       ├── 是否为工具类/纯函数？
    │       │       │       │   ├── 是 → 程序直接调用
    │       │       │       │   └── 否 → 程序直接调用
    └── 前端与后端 → HTTP API
    └── 第三方/外部系统 → HTTP API
```

## 示例场景

| 场景 | 选择 | 说明 |
|------|------|------|
| 订单服务调用库存服务 | HTTP API | 不同微服务，跨进程 |
| OrderService调用OrderRepository | Interface定义 | 可能切换实现（JPA/MyBatis），需Mock测试 |
| OrderService调用PaymentService | Interface定义 | 支付渠道可能切换（支付宝/微信），需Mock测试 |
| PaymentService调用AlipayClient | 程序直接调用 | 具体实现类，无替换需求 |
| OrderController调用OrderService | Interface定义 | Service层面向接口，Controller依赖接口非实现 |
| StringUtils.isEmpty() | 程序直接调用 | 工具方法，无状态无多态 |
| 前端页面调用后端接口 | HTTP API | 前后端分离，跨运行环境 |
| OrderService调用LogService | 程序直接调用 | 同进程内日志服务，调用关系固定 |
