# 云设计模式

> 来源：[awesome-copilot/cloud-design-patterns](https://github.com/github/awesome-copilot/tree/main/skills/cloud-design-patterns) + [Azure Architecture Center](https://learn.microsoft.com/azure/architecture/patterns/)
>
> 42种技术无关的云设计模式，适用于任何分布式系统（Azure/AWS/GCP/本地/混合环境）。

## 分布式计算谬误

在使用这些模式前，应意识到分布式计算的常见谬误：
1. 网络是可靠的
2. 延迟为零
3. 带宽是无限的
4. 网络是安全的
5. 拓扑不会变化
6. 只有一个管理员
7. 组件版本化很简单
8. 可观测性可以延后实施

## 模式分类总览

| 类别 | 模式数量 | 关注点 |
|------|----------|--------|
| 可靠性与韧性 | 9 | 容错、自愈、优雅降级 |
| 性能 | 10 | 缓存、扩展、负载管理、数据优化 |
| 消息与集成 | 7 | 解耦、事件驱动通信、工作流协调 |
| 架构与设计 | 7 | 系统边界、API网关、迁移策略 |
| 部署与运维 | 5 | 基础设施管理、地理分布、配置 |
| 安全 | 3 | 身份、访问控制、内容校验 |
| 事件驱动架构 | 1 | 事件溯源与审计追踪 |

## 可靠性与韧性模式（9种）

| 模式 | 适用场景 | 核心思想 |
|------|----------|----------|
| Ambassador（大使） | 需要统一处理外部服务通信 | 用代理服务处理连接管理、重试、安全等 |
| Bulkhead（舱壁） | 需要隔离故障防止级联 | 将系统分区，一个分区故障不影响其他 |
| Circuit Breaker（熔断器） | 防止级联故障 | 检测故障后中断连接，定期试探恢复 |
| Compensating Transaction（补偿事务） | 长事务需要回滚 | 用补偿操作撤销已提交的步骤 |
| Retry（重试） | 瞬时故障恢复 | 自动重试失败的操作，指数退避 |
| Health Endpoint Monitoring（健康端点监控） | 运行时健康检查 | 暴露健康检查端点供监控系统调用 |
| Leader Election（领导者选举） | 需要单一协调者 | 通过选举确定主节点，避免竞争 |
| Saga（传奇） | 跨服务分布式事务 | 编排一系列本地事务+补偿操作 |
| Sequential Convoy（顺序车队） | 消息必须按序处理 | 按序路由消息到同一处理器 |

## 性能模式（10种）

| 模式 | 适用场景 | 核心思想 |
|------|----------|----------|
| Async Request-Reply（异步请求-回复） | 长时间运行的操作 | 异步处理，通过轮询/Webhook获取结果 |
| Cache-Aside（旁路缓存） | 提高读取性能 | 按需加载数据到缓存，缓存未命中时回源 |
| CQRS（命令查询职责分离） | 读写负载差异大 | 分离读模型和写模型，独立优化 |
| Index Table（索引表） | 数据按多种方式查询 | 创建次级索引表加速查询 |
| Materialized View（物化视图） | 预计算复杂查询 | 预生成查询结果视图 |
| Priority Queue（优先级队列） | 请求优先级不同 | 按优先级排序处理队列消息 |
| Queue-Based Load Leveling（队列负载均衡） | 平滑流量高峰 | 用队列缓冲请求，消费者按自身速率处理 |
| Rate Limiting（限流） | 防止资源过载 | 限制单位时间内的请求数量 |
| Sharding（分片） | 数据量过大 | 按分片键分布数据到不同存储节点 |
| Throttling（节流） | 控制资源消耗 | 限制应用实例的资源使用率 |

## 消息与集成模式（7种）

| 模式 | 适用场景 | 核心思想 |
|------|----------|----------|
| Choreography（编舞） | 服务间协调 | 每个服务自主响应事件，无中央协调器 |
| Claim Check（提取单） | 大消息传输 | 消息体存存储，只传引用ID |
| Competing Consumers（竞争消费者） | 提高消息处理吞吐 | 多个消费者并行消费同一队列 |
| Messaging Bridge（消息桥） | 异构消息系统互通 | 桥接不同消息系统间的消息 |
| Pipes and Filters（管道与过滤器） | 复杂消息处理流水线 | 将处理分解为独立过滤器串联 |
| Publisher-Subscriber（发布-订阅） | 事件广播 | 发布者广播事件，订阅者按需接收 |
| Scheduler Agent Supervisor（调度-代理-监控） | 分布式工作流编排 | 调度器分配任务，代理执行，监控器监督 |

## 架构与设计模式（7种）

| 模式 | 适用场景 | 核心思想 |
|------|----------|----------|
| Anti-Corruption Layer（反腐层） | 集成遗留系统 | 用转换层隔离不同模型 |
| Backends for Frontends（BFF） | 不同前端需求差异 | 为每种前端创建专用后端 |
| Gateway Aggregation（网关聚合） | 减少前端多次调用 | 网关聚合多个后端请求 |
| Gateway Offloading（网关卸载） | 共享横切关注点 | 将SSL/认证等移至网关 |
| Gateway Routing（网关路由） | 统一入口路由 | 用网关将请求路由到不同服务 |
| Sidecar（边车） | 独立管理横切关注点 | 伴随主服务的辅助进程 |
| Strangler Fig（绞杀者无花果） | 渐进式系统迁移 | 逐步替换旧系统组件 |

## 部署与运维模式（5种）

| 模式 | 适用场景 | 核心思想 |
|------|----------|----------|
| Compute Resource Consolidation（计算资源整合） | 提高资源利用率 | 合并多个任务到同一计算单元 |
| Deployment Stamps（部署印记） | 多租户/多区域 | 每个租户/区域独立部署副本 |
| External Configuration Store（外部配置存储） | 统一配置管理 | 将配置从应用中提取到集中存储 |
| Geode（宝石） | 低延迟全球访问 | 在多区域部署数据副本 |
| Static Content Hosting（静态内容托管） | 提高静态资源性能 | 将静态内容部署到CDN/对象存储 |

## 安全模式（3种）

| 模式 | 适用场景 | 核心思想 |
|------|----------|----------|
| Federated Identity（联合身份） | 跨组织身份认证 | 委托外部身份提供者认证 |
| Quarantine（隔离） | 内容安全验证 | 在安全区验证外部内容后才允许使用 |
| Valet Key（代客泊车钥匙） | 有限资源访问授权 | 提供有限权限的令牌给客户端直接访问资源 |

## 事件驱动架构模式（1种）

| 模式 | 适用场景 | 核心思想 |
|------|----------|----------|
| Event Sourcing（事件溯源） | 完整审计追踪 | 所有状态变更以事件序列存储，可重放恢复状态 |

## 模式选择指引

选择模式时应关注"为什么选择"而非"如何实现"：

1. **识别问题** - 哪些分布式计算谬误正在影响系统？
2. **匹配模式** - 该谬误对应哪些模式？
3. **评估权衡** - 每个模式有哪些取舍？
4. **组合使用** - 多个模式如何协同工作？
5. **验证效果** - 引入模式后问题是否得到缓解？
