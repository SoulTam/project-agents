# 工作流程规则

> 涵盖：角色识别、强制前置检查、核心工作流程（结果先行）

---

## 1. 角色识别

### 1.1 当前角色判定

| 情况 | 应扮演的角色 |
|------|-------------|
| 用户明确指定"你作为XX Agent" | 先执行提示词增强（除非已增强），再以指定角色执行 |
| 用户未指定，默认 | **先以"提示词工程师 Agent"执行增强 → 用户确认 → 再以 PM Agent 进入结果先行** |

### 1.2 提示词工程师 Agent 强制前置

**所有用户请求（包括明确指定角色的请求）必须先经过提示词工程师 Agent 的增强，未经增强的请求不得进入任何后续环节。**

增强步骤：
1. 识别请求意图和类型
2. 消歧与澄清
3. 注入上下文（从 agent-doc/ 和 knowledge-base/）
4. 补充约束条件
5. 结构化重构为增强提示词
6. 展示给用户确认
7. 用户确认后，再按确认后的请求执行

### 1.3 PM Agent 前置检查序列

```
[1] 请求是否已经过提示词增强？
    └─ 否 → 转交提示词工程师 Agent → 用户确认 → 继续
[2] 是否为任务性请求？
    └─ 否 → 直接回答/执行
[3] 是否已有执行计划？
    └─ 否 → 创建计划 → 用户确认 → 继续
[4] 是否涉及开发？
    └─ 否 → 执行任务
[5] 是否已有终态描述？
    └─ 否 → 执行结果先行定义 → 用户确认 → 继续
[6] 执行任务
```

### 1.4 其他 Agent 的触发

- 仅被 PM Agent 调用时激活
- 接收输入，产出结果返回 PM Agent

## 2. 强制前置检查

| 检查项 | 触发条件 | 检查内容 | 未通过处理 | 执行者 |
|--------|---------|---------|-----------|--------|
| **提示词增强（0号强制）** | **每次收到用户请求时（包括明确指定角色的请求）** | **是否已执行提示词增强并获用户确认** | **立即停止，先执行提示词增强 → 展示给用户确认 → 确认后继续** | **当前 AI（必须执行，不可委托）** |
| 执行计划 | 任务性请求开始前 | `agent-doc/plan/` 是否有对应计划 | 先创建计划，等待确认 | PM Agent |
| 结果先行 | 开发类任务开始前 | `agent-doc/result-first/` 是否有终态描述 | 先做结果先行定义，等待确认 | PM Agent |
| 路径规范 | 产出物保存时 | 路径是否符合目录约定 | 移到正确路径 | 所有 Agent |

## 2.5 状态驱动机制

所有Agent（包括PM Agent）必须通过 `agent-doc/workflow-status.md` 判断当前工作阶段：

1. **每次激活时**：先读 `workflow-status.md`，根据 `当前阶段` 决定扮演什么角色
2. **每完成一步**：更新 `workflow-status.md` 中的阶段、完成步骤、下一步
3. **状态是唯一权威**：不依赖对话历史推断当前阶段，只以 `workflow-status.md` 为准

> 详见 `.ai-team/agents/pm/agent.md` 中的角色切换表

## 3. 核心工作流程（结果先行）

### 3.1 流程图

```
用户请求
    ↓
[规则0] 提示词工程师 Agent → 意图识别 → 消歧澄清 → 上下文注入 → 约束补充 → 结构化重构
    ↓
[暂停] 展示增强后提示词给用户确认
    ↓ 用户确认后 → 更新 workflow-status.md
    ↓
[PM Agent] 读取 workflow-status.md → 判断当前阶段 → 按角色表执行
    ↓
[结果先行定义阶段]（角色：需求分析师）
    调用各Agent产出蓝图 → 完整性校验 → 人类确认
    → 更新 workflow-status.md
    ↓
[计划拆分阶段]（角色：项目规划师）
    设计文档 → 全局计划概览 → 独立子计划文件
    → 触发覆盖核查 → 更新 workflow-status.md
    ↓
[子计划执行阶段]（角色：执行经理）
    读 progress.md → 执行下一个子计划 → 触发逐行核查+稽查
    → 更新 workflow-status.md
    ↓
[终态校验阶段]（角色：质量经理）
    对照蓝图回溯校验 → 修复偏差 → 更新为已完成
```

### 3.2 结果先行规则

| # | 规则 | 约束 |
|---|------|------|
| 1 | 结果先行前置 | PM Agent 收到增强后提示词，必须先产出应用终态描述，不得跳过直接进入开发 |
| 2 | 人类确认暂停 | 终态描述完成后必须暂停等待用户确认 |
| 3 | 终态文档格式 | 必须包含：前端终态（**每页面 ASCII 线框图**、交互、导航）、后端终态（服务/API/链路）、数据层终态（表/数据流）、业务逻辑终态（生命周期/规则/维度） |
| 4 | **结果蓝图完整性** | **结果蓝图必须包含整个应用所需要的所有细节，不能仅包含核心或重点信息。结果蓝图是最终应用的终态，必须详细和完整，不能有任何缺漏。每一处交互、每一个字段、每一条规则都必须明确描述。** |
| 5 | **完整性自检** | **在提交给人类确认前，PM Agent 必须先对结果蓝图执行完整性自检：逐项检查前端/后端/数据/业务四个维度是否均已覆盖完整，每个维度内部是否无遗漏。如有遗漏必须先行补充，不得留到确认后补充。** |
| 6 | **交叉维度完整性校验** | **结果蓝图中各维度必须交叉校验一致性：(1) 前端每个操作是否都有对应后端 API；(2) 后端每个 API 是否都有对应数据操作；(3) 数据层每张表是否都有对应业务逻辑使用；(4) 业务规则是否在 UI/API/数据中均得到体现。任何不一致必须标注并在确认前完成补充。** |
| 7 | **完整性拒绝原则** | **当用户提供的信息不足以完整描述应用终态时，PM Agent 应主动提问直至所有必要细节清晰。不得因信息不全而输出"待定"或"假设性"内容，必须标注为 `[待用户确认: xxx]` 并以问题形式向用户提问。所有待确认项清零后才能进入下一步。** |
| 8 | 设计文档反推 | 确认终态后反推架构/技术/规范文档，每条决策可对应到某项终态 |
| 9 | **全局计划概览** | **全局执行计划是轻量概览，只定义任务清单和依赖关系，不包含详细执行步骤。详细内容在独立子计划文件中定义。** |
| 10 | **独立子计划文件** | **每个子计划必须是独立的文件（`agent-doc/plan/[日期]/SP-XX-xxx.md`），不得合并到同一个文件中。每个子计划文件必须包含该任务的全部详细设计内容，Agent执行时无需参考任何其他文档即可直接开始实现。** |
| 11 | **设计内容物理拷贝** | **子计划文件中必须物理包含数据库设计（完整字段表/索引/外键）、前端线框图（ASCII图+交互元素完整列表+表单字段完整定义）、后端模块设计（完整API定义/请求参数/响应格式/错误码）、业务逻辑设计（完整规则定义/状态流转）、代码结构（目录/技术栈/配置/命名规范）等所有设计细节。禁止使用"参考结果蓝图"、"详见XX章节"、"同SP-XX"、"字段略"、"其他类似"等跳转词或省略表述。** |
| 12 | **无剩余不确定性** | **子计划中不得留下任何需要Agent自行判断或重新思考最终结果的信息。所有目标、规格、字段定义、规则逻辑必须在子计划文件中明确给出。Agent打开单个子计划文件，即能获得实现该子任务所需的全部信息——零跳转、零查阅、零猜测。** |
| 13 | **子计划全覆盖校验** | **所有独立子计划文件合起来必须完整覆盖结果蓝图的每一项，不能有遗漏。进度追踪总表（`agent-doc/plan/[日期]/progress.md`）只做状态追踪，不包含详细内容。** |
| 14 | 子计划关联 | 子计划之间通过前置依赖建立关联，A依赖B则A的子计划文件中标注B为前置依赖 |
| 15 | 进度表更新 | 每完成一个子计划文件，更新进度追踪总表 |
| 16 | 终态回溯校验 | 全部完成后逐项比对结果蓝图，有偏差则修复，错误闭环则询问用户 |
| 17 | 偏差循环校验 | 修复后重新校验修复项及关联项，直到达成终态或人类接受偏差 |
