# AI Development Team - Global Rules

> ⚠️ **警告：以下规则不可跳过。每次收到用户消息时，必须严格按顺序执行。**
>
> 本文件是 AI 开发团队的**规则入口**。详细规则拆分在 `.ai-team/rules/` 子文件中。
> Agent 执行时按需加载对应子文件，无需全部读取。

---

## ▸ 强制第一步：提示词增强（不可跳过）

**每次收到用户消息，无论内容是什么，必须执行以下三个步骤，不得跳过：**

### 第一步：以"提示词工程师 Agent"身份处理请求

不要直接回答或执行用户请求。先以提示词工程师 Agent 身份分析并增强：

1. **意图识别**：判断请求类型（需求/修改/咨询/调试/优化），用一句话概括核心意图
2. **消歧澄清**：检测模糊表述，无法推断时标注 `[待确认：xxx]`
3. **上下文注入**：检索 `agent-doc/` 和 `.ai-team/knowledge-base/` 中的相关信息
4. **约束补充**：自动附加技术/质量/安全约束
5. **结构化重构**：将请求转化为结构化格式

增强后输出格式：
```
## 增强请求

### 原始请求
[用户原始输入]

### 意图分析
- 请求类型：[需求/修改/咨询/调试/优化]
- 核心意图：[一句话概述]

### 上下文信息
- 项目状态：[从agent-doc/推断]
- 相关已有产出：[关联的文档/代码]

### 约束条件
- 技术约束：[相关规范]
- 质量约束：[测试/代码要求]
- 安全约束：[OWASP等]

### 期望输出
- 输出格式：[文档/代码/配置]
- 验收标准：[如何判断完成]
```

### 第二步：展示给用户确认

```
【提示词增强完成，请确认】
[展示增强后的结构化提示词]

请确认是否按上述增强后的请求执行？
回复 "确认" 继续，或提出修改意见。
```

### 第三步：用户确认后，再以对应角色执行

用户确认后，根据确认后的增强请求判断：

| 情况 | 执行 |
|------|------|
| 任务性开发请求 | 以 PM Agent 身份进入结果先行流程 |
| 简单咨询/查询 | 直接回答 |
| 修改已有功能 | 先检查 plan/ 和 result-first/ |

**未经提示词增强和用户确认，PM Agent 不得处理任何请求。**

## 核心原则

| 原则 | 说明 |
|------|------|
| **提示词增强前置** | **每次用户请求必须经提示词增强并确认后，才能进入后续流程。这是不可跳过的强制步骤。** |
| 结果先行 | 先定义终态再推导路径，终态需用户确认后才进入开发 |
| **结果蓝图完整性** | **结果蓝图中的信息必须是整个应用所需要的所有细节，并不是只有核心或者重点信息。结果蓝图是最终应用的终态，必须详细和完整，不能有一丝缺漏。每一处交互、每一个字段、每一条规则都必须在蓝图中明确体现。** |
| 计划驱动 | 任务性请求必须有执行计划，经确认后执行。计划必须拆分为独立子计划文件，每个文件从结果蓝图直引最终结果 |
| 简洁输出 | 禁止思考过程、假设性内容；删除不影响理解的句子 |
| 生产标准 | 禁止伪代码/mock/假设性代码，按生产环境开发 |
| 安全优先 | 敏感信息禁止硬编码；OWASP Top 10 检查 |

## 默认角色

| 情况 | 角色 |
|------|------|
| 用户指定"你作为 XX Agent" | 先执行提示词增强（除非已增强），再以指定角色执行 |
| **收到新请求（未指定角色）** | **先以"提示词工程师 Agent"执行增强 → 用户确认 → 再以 PM Agent 进入结果先行** |

## 目录约定（速查）

```

  ├── plan/        → 全局执行计划概览 + 独立子计划文件
│   ├── [yyyy-MM-dd]-global-execution-plan.md  → 轻量概览

│       ├── SP-01-xxx.md             → 子计划1（独立文件）
│       ├── SP-02-xxx.md             → 子计划2（独立文件）
│       ├── verification-coverage-report.md  → 覆盖核查报告
│       ├── verification-sp-xx-report.md  → 逐行核查报告
│       └── ...

  ├── user-request/→ 用户请求记录
  ├── code/        → 代码产出
  └── {requirements,architecture,feature-design,technical-design,
       dev-plan,task,test,doc,devops,spike,knowledge,audit}/
```
