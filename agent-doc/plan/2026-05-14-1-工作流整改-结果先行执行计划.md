## 一、整改背景

当前AI团队采用"需求→分析→设计→开发→测试"的传统流水线模式，存在以下问题：

1. **目标偏离**：各Agent逐步推进时，容易在细节中迷失，最终产出与初始需求偏离
2. **缺乏终态锚定**：没有在项目初期明确"做完之后应该是什么样子"，导致中间环节各自理解不一致
3. **纠偏滞后**：偏差往往在开发后期才被发现，修复成本高
4. **计划脱节**：拆分后的子计划可能各自为政，缺乏关联性校验

## 二、整改核心思路：结果先行

**核心原则**：在项目初期，先定义应用"成熟时的样子"，再反向推导如何到达。

### 新旧流程对比

```
【旧流程】
用户需求 → 提示词增强 → PM分发 → 需求分析 → 架构设计 → 功能设计 → 技术设计 → 开发计划 → 任务分配 → 开发 → 测试
          ↑ 问题：每个环节向前看，缺乏统一终点锚定

【新流程】
用户需求 → 提示词增强 → PM → 【结果先行定义】→ 人类确认 → 开发/设计文档 → 全局执行计划 → 进度表 → 计划拆分 → 逐项执行 → 偏差校验
          ↑ 关键：先明确终点，再规划路径
```

### 新增关键阶段

| 阶段 | 名称 | 产出物 | 确认方 |
|------|------|--------|--------|
| 新增 | **结果先行定义** | 应用终态描述文档 | 人类用户 |
| 新增 | **开发/设计文档输出** | 设计文档、开发文档 | - |
| 新增 | **全局详细执行计划** | 全局计划文档 | - |
| 新增 | **进度表** | 拆分计划进度表 | - |
| 新增 | **计划拆分与关联校验** | 关联子计划集 | - |
| 新增 | **终态回溯校验** | 校验报告 | 人类用户（偏差时） |

## 三、详细执行计划

### 步骤1：更新PM Agent定义

**目标**：PM Agent增加"结果先行"阶段职责

**修改文件**：`.ai-team/agents/pm/agent.md`

**修改内容**：
- 在PM Agent的工作流程中，接收增强后提示词的第一步改为：调用相关Agent进行"结果先行定义"
- PM Agent需判断需求类型，确定需要调用哪些Agent参与结果定义
- 结果定义完成后，暂停等待人类用户确认
- 人类确认后才进入后续开发文档输出阶段

**预计影响范围**：PM Agent自身

---

### 步骤2：新增"结果先行定义"Skill

**目标**：创建标准化的结果先行定义方法论

**新增文件**：`.ai-team/skills/pm/result-first-definition/skill.md`

**Skill内容要点**：
1. **前端终态定义**：
   - 每个页面的布局描述（线框级）
   - 页面中的交互元素（按钮、表单、列表等）及其功能
   - 页面间导航/切换关系
   - 表单字段、校验规则、提交行为
   - 数据展示方式和格式

2. **后端终态定义**：
   - 提供给前端的每个服务/接口
   - 接口与前端操作的对应关系
   - 后端处理链路（请求→处理→响应的完整流程）
   - 每个处理环节的职责

3. **数据层终态定义**：
   - 数据库表/集合设计
   - 数据如何被各功能使用
   - 数据流向图

4. **业务逻辑终态定义**：
   - 核心业务对象的完整生命周期
   - 业务规则和约束
   - 状态流转

5. **管理维度终态定义**：
   - 各管理对象（如Agent、Skill）的CRUD完整描述
   - 管理操作的权限和边界

**预计影响范围**：新增Skill文件

### 步骤3：新增"开发/设计文档输出"Skill

**目标**：基于确认后的终态结果，反向输出设计文档和开发文档

**新增文件**：`.ai-team/skills/pm/design-doc-generation/skill.md`

**Skill内容要点**：
1. **输入**：人类确认后的"结果先行定义"文档
2. **输出**：
   - 架构设计文档（基于终态反推架构选型、模块划分）
   - 技术设计文档（基于终态反推接口定义、数据模型、技术方案）
   - 开发规范文档（基于终态确定编码规范、项目结构）
3. **方法**：从终态描述中提取技术约束和设计决策

**预计影响范围**：新增Skill文件

---

### 步骤4：新增"全局执行计划制定"Skill

**目标**：基于设计文档，制定环环相扣的全局详细执行计划

**新增文件**：`.ai-team/skills/pm/global-execution-planning/skill.md`

**Skill内容要点**：
1. **输入**：设计文档、开发文档
2. **输出**：全局详细执行计划
3. **计划要求**：
   - 每个任务有明确的输入依赖和输出产物
   - 任务间有明确的前后依赖关系
   - 任务粒度适中（单个任务不超过1个开发会话）

**预计影响范围**：新增Skill文件

---

### 步骤5：新增"计划拆分与进度追踪"Skill

**目标**：将全局计划拆分为可执行的子计划，并建立进度追踪表

**新增文件**：`.ai-team/skills/pm/plan-breakdown-tracking/skill.md`

**Skill内容要点**：
1. **进度表格式**：
   ```
   | 编号 | 子计划名称 | 依赖项 | 关联子计划 | 状态 | 完成标志 |
   |------|-----------|--------|-----------|------|---------|
   | P-01 | xxx      | 无     | P-02,P-03 | ⬜待开始 | xxx产出 |
   | P-02 | xxx      | P-01   | P-04      | ✅已完成 | xxx产出 |
   ```
2. **拆分规则**：
   - 每个子计划必须关联至少一个其他子计划（首尾计划除外）
   - 每个子计划必须标注依赖项，依赖项未完成则不可开始
   - 子计划间不能脱节，必须有数据/产物传递关系
3. **进度更新规则**：
   - 每完成一个子计划，更新进度表对应item状态为✅
   - 完成时记录实际产出，与计划产出比对

**预计影响范围**：新增Skill文件

---

### 步骤6：新增"终态回溯校验"Skill

**目标**：所有子计划完成后，回溯校验是否能达到初始定义的终态

**新增文件**：`.ai-team/skills/pm/result-rollback-verification/skill.md`

**Skill内容要点**：
1. **校验流程**：
   - 逐项检查所有子计划产出，与"结果先行定义"文档逐条对比
   - 标记：✅已达成 / ⚠️有偏差 / ❌缺失
   - 生成偏差报告
2. **偏差处理**：
   - 有偏差：修复计划细节，调整相关子计划
   - 错误闭环（无法确定修复方案）：暂停并询问人类用户
3. **循环校验**：
   - 修复后重新校验，直到所有项✅或人类确认接受偏差

**预计影响范围**：新增Skill文件

```
步骤1(PM Agent) ──→ 步骤9(需求Agent) ──→ 步骤2(结果先行Skill)

                  ├──→ 步骤11(功能Agent) ─┤
                  └──→ 步骤12(技术Agent) ─┘
                                              │
步骤2(结果先行Skill) → 步骤3(设计文档Skill) → 步骤4(全局计划Skill)
                                                │
步骤4(全局计划Skill) → 步骤5(拆分追踪Skill) → 步骤6(回溯校验Skill)
                                                │
步骤1-6完成 → 步骤7(全局规则) → 步骤8(README)
```

**关键依赖**：
- 步骤2-6的Skill必须按顺序创建，因为后续Skill依赖前序Skill的产出
- 步骤9-12的Agent更新可并行进行
- 步骤7（全局规则）需在步骤1-6完成后执行，确保规则与实际Skill一致
- 步骤8（README）最后执行，汇总所有变更

## 六、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 结果先行定义过于笼统，后续无法指导开发 | 开发阶段仍会偏离 | Skill中定义细粒度模板，确保每个交互元素都有描述 |
| 人类确认环节耗时过长 | 项目启动延迟 | 结果先行文档分章节输出，可分段确认 |
| 计划拆分过细导致管理开销大 | 执行效率降低 | 单个子计划粒度控制在1个开发会话内 |
| 终态回溯校验发现大量偏差 | 返工成本高 | 关键校验点前置，在子计划执行中增加阶段性校验 |
